Ⅰ. 프로젝트 개요

1. 개발 배경 및 필요성

1) 레거시 객체 지향(OOP) 아키텍처의 한계

대다수 상용 게임, 렌더링 엔진은 과거 프로젝트와의 호환을 위해 객체 지향(OOP) 기반 씬 그래프와 두꺼운 추상화 계층을 유지합니다. 다중 상속과 가상 함수 중심의 구조는 객체를 메모리에 흩어 놓아, 런타임에 포인터 추적(pointer chasing)과 가상 호출을 반복하게 만듭니다. 이러한 접근 패턴은 CPU 캐시 미스를 늘려, 코어 수가 늘어도 처리량이 비례해 오르지 못하는 원인이 됩니다. (캐시 미스가 성능에 미치는 원인과 측정은 Ⅲ.1에서 다룹니다.)

아래의 사진은 OOP 구조가 가지는 가상함수 테이블 구조와 그에 따른 숨겨진 비용들이 어떻게 캐시 미스를 유발하는지에 대한 컨퍼런스의 한 장면입니다.

2) 현대 그래픽스 API의 하드웨어 제어 철학

DirectX 12와 Vulkan은 기존 드라이버가 상당 부분 추적하던 리소스 상태와 동기화 책임을 애플리케이션으로 옮긴 명시적 그래픽스 API입니다. Metal 역시 command buffer/encoder와 pipeline state 중심의 낮은 오버헤드 제어 모델을 제공하여, 개발자가 GPU 작업의 구성과 제출 흐름을 더 직접적으로 다루게 합니다. 이러한 API의 공통된 방향은 드라이버가 숨겨주던 비용을 줄이는 대신, 엔진이 리소스 수명, 배리어, 파이프라인 상태, 커맨드 기록 방식을 스스로 설계하도록 요구한다는 점입니다.

설계 철학	핵심 메커니즘	기대 효과
상태 객체의 불변화	Pipeline State Object 베이킹(Baking)	런타임 유효성 검사 비용 및 / 파이프라인 스톨(Stall) 제거
명시적 메모리 배열화	모든 리소스 뷰의 1차원 연속 배열화	포인터 체이싱(Pointer Chasing) 폐기 및 데이터 지역성 확보
Lock-Free 멀티 스레딩	워커 스레드별로 독립적인 커맨드, 메모리 할당	병렬 기록 시 전역 Mutex Lock 차단

그러나 명시적 API를 사용하더라도 두꺼운 범용 래퍼나 구형 상태 기계식 추상화를 얹으면, API가 제공하는 직접 제어와 멀티 스레드 기록의 이점이 응용 단계(렌더링 파이프라인의 단계 중 하나)까지 충분히 드러나지 않을 수 있습니다. 따라서 본 프로젝트는 레거시 호환을 우선하는 범용 래퍼보다, 하드웨어 캐시 구조와 명시적 자원 모델에 맞춘 얇은 데이터 지향 프레임워크(DOD, Data-Oriented Design)를 목표로 합니다.

이 목표를 구체화하기 위해 다음 절에서는 프레임워크의 계층 구조, 사용자 시나리오, RHI와 렌더링 파이프라인의 개발 내용을 설명합니다.

2. 개발 내용

1) 시스템 아키텍처 구성도

앞 절에서 제시한 목표를 구현하기 위해 본 프레임워크는 편의 기능을 하나의 두꺼운 객체 계층에 모으지 않고, 데이터 흐름과 제어 책임에 따라 네 계층으로 분리합니다. 하위 Foundation은 캐시 친화적 데이터 처리와 멀티스레딩 기반을 제공하고, RHI는 Vulkan·D3D12·Metal의 명시적 자원 모델을 얇게 노출합니다. 그 위의 Render Graph는 패스 간 리소스 수명과 배리어를 관리하며, Render Front-End는 사용자가 장면과 재질을 다루는 상위 진입점 역할을 합니다.

2) 시스템 서비스 시나리오

본 프레임워크의 사용자는 상위 렌더러를 이용해 기본 렌더링 경로를 구성할 수 있으며, 필요한 경우 RHI까지 내려가 API 별 세부 동작을 직접 제어할 수 있습니다. 일반적인 사용 흐름은 플랫폼 선택, 리소스 생성, 렌더 패킷 구성, 커맨드 기록 및 제출 순서로 이루어집니다.

멀티 플랫폼 실행의 경우, 사용자는 `IDevice::Create`를 통해 실행 환경에 맞는 백엔드(Vulkan·D3D12·Metal)를 선택합니다. 이후 버퍼·텍스처 생성, 파이프라인 설정, 드로우 호출은 공통 인터페이스를 통해 수행되므로, 상위 렌더링 코드는 API 호출에 직접 의존하지 않습니다.

===== 5쪽 =====

성능 조정이 필요한 경우에는 제어 깊이를 단계적으로 선택합니다. 기본 경로는 `RendererDesc`로 바인딩 방식, 포맷, 조명, 그림자 설정을 조정하고, 더 낮은 수준의 제어가 필요할 때는 상위 렌더러의 저수준 API나 `IDevice`·`ICommandList`를 직접 사용합니다. 이 구조는 추상화를 고정된 장벽으로 두지 않고, 기능 구현 단계와 성능 분석 단계에서 필요한 만큼 낮은 계층으로 접근할 수 있게 합니다.

대규모 오브젝트 렌더링에서는 렌더 패킷을 평탄화하고 정렬하여 상태 변경과 드로우 제출 비용을 줄입니다. 리소스 바인딩은 백엔드별 디스크립터/argument 리소스 테이블과 소량 상수 전달 경로로 추상화하여, 다수의 텍스처와 버퍼를 일관된 방식으로 참조하도록 설계합니다.

멀티코어 활용은 현재 설계·진행 중인 영역입니다. 워커 스레드별 독립 커맨드 리스트와 할당자를 두어 커맨드 기록 단계의 전역 경합을 줄이고, 최종 제출 시에는 정렬된 렌더 패킷과 의존성 정보를 기준으로 실행 순서를 확정하는 구조를 목표로 합니다.

따라서 본 프레임워크는 편의 기능을 제공하면서도, 필요한 경우 사용자가 구성 설정, 상위 렌더러의 저수준 API, RHI 직접 사용 순으로 제어 범위를 넓힐 수 있도록 설계합니다. 이러한 점진적 제어 방식이 기존 렌더링 라이브러리와 어떤 차이를 갖는지는 다음 장에서 비교합니다.

Ⅱ. 관련 작품 분석

1. 관련 작품 설명

1) bgfx

bgfx는 광범위한 플랫폼과 그래픽스 API를 단일 인터페이스로 묶어 제공하는, 사실상 업계 표준급으로 널리 쓰이는 렌더링 라이브러리입니다. 공식 지원 API는 Direct3D 11·12, Metal, OpenGL, OpenGL ES, Vulkan, WebGL, WebGPU 등을 포함하며, 서로 다른 API 차이를 공통 인터페이스로 흡수하는 데 강점이 있습니다. 다만 이러한 범용성은 응용 코드가 네이티브 D3D12/Vulkan 수준의 리소스 상태, 배리어, 디스크립터 바인딩 정책을 직접 다루기보다 bgfx가 제공하는 추상화와 내부 변환에 의존한다는 뜻이기도 합니다. 따라서 본 프로젝트가 목표로 하는 얇은 RHI와 세부 제어 경로를 기준으로 보면, bgfx는 이식성과 안정성을 우선한 범용 렌더링 계층에 가깝습니다.

2) Methane Kit

Methane Kit은 DirectX 12·Vulkan·Metal 등 최신 네이티브 그래픽스 API 위에서 동작하는 C++20 기반 크로스플랫폼 프레임워크입니다. 공식 설명에서도 객체 지향 중간 수준 그래픽스 API를 제공한다고 밝히며, 사용 편의성과 플랫폼 독립성을 중요한 목표로 둡니다. 이 방향은 최신 API를 대상으로 한다는 점에서는 본 프로젝트와 유사하지만, 추상화의 중심이 객체 지향 RHI 인터페이스에 있다는 점에서 차이가 있습니다. 본 프로젝트는 기능 편의보다 얇은 데이터 컨테이너, 명시적 자원 모델, 필요 시 RHI 직접 접근이 가능한 점진적 제어를 우선합니다.

2. 차별성 및 우수성

요약하면 본 프레임워크의 차별성은 '모든 API를 포괄하는 범용성'이나 '객체 지향 중간 수준 API의 편의성'이 아니라, 최신 명시적 API의 이점을 가리지 않는 얇고 데이터 지향적인 설계에 있습니다. 이는 호환성과 이식성을 우선하는 bgfx, 사용 편의성을 강조하는 Methane Kit과 구분되는 지점입니다.

1) CPU 캐시 아키텍처 및 물리적 메모리 레이아웃

메모리는 단일 속도가 아니라 계층(L1-L2-L3-주 메모리)으로 구성되며, 하위로 갈수록 용량은 크지만 지연이 급격히 늘어납니다. 한 번의 미스로 주 메모리까지 내려가면 수백 사이클, 곧 수백 개 명령을 실행할 시간을 대기로 소모할 수 있습니다 (Drepper, 2007). 데이터는 바이트 단위가 아니라 CPU 캐시 라인 단위로 캐시에 적재됩니다.

계층	대략적 접근 지연	비고
L1	약 4 사이클
L2	약 12 사이클
L3	약 40 사이클
주 메모리	약 100-300 사이클	1회 미스 = 수백 명령 분량 대기

(대략치이며 CPU에 따라 다릅니다. 출처: Drepper, 2007.)

객체 지향 씬 그래프처럼 포인터로 흩어진 객체를 따라가는 접근(pointer chasing)과 가상 함수 테이블 간접 호출은 매 접근이 미스가 되기 쉽습니다. Albrecht(2009)는 OOP 씬 그래프 순회에서 객체당 다수의 L2 미스를 측정하고, 데이터 지향 재배치로 프레임 시간을 19.2ms에서 3.3ms로 단축한 사례를 보고합니다.

2) 데이터 지향 설계에 입각한 SoA(Structures of Arrays) 구조에 관한 연구

캐시 계층의 관점에서 보면 중요한 것은 “필요한 데이터가 같은 캐시 라인 안에 얼마나 조밀하게 모여 있는지” 입니다. 객체 지향 엔진에서 흔히 나타나는 객체 단위 AoS 배치는 한 객체의 여러 필드를 함께 저장합니다. 그러나 특정 필드만 순회하는 작업(예: 위치 갱신)에서는 캐시 라인에 함께 들어온 나머지 필드가 사용되지 않아 라인의 유효 바이트율이 떨어집니다. 반대로 SoA는 같은 필드를 연속 배열로 분리하므로, 해당 작업이 읽는 데이터가 캐시 라인을 더 효율적으로 채웁니다. 이러한 포인터 추적과 연속 배열의 대비는 데이터 지향 설계의 출발점입니다 (Acton, 2014).

3) SIMD 인트린직(Intrinsics)을 활용한 데이터 병렬 처리 성능 측정

SoA는 캐시 지역성뿐 아니라 SIMD 활용에도 유리합니다. 같은 타입의 데이터가 연속으로 놓이면 SIMD 레지스터에 그대로 적재(load)하여 한 명령으로 여러 요소를 처리할 수 있는 반면, AoS는 흩어진 필드를 모으는 gather·shuffle 비용이 들 수 있습니다. 본 측정에서는 SSE의 128비트 XMM 레지스터(`__m128`)를 사용하는 인트린직 구현과 스칼라 구현을 비교했습니다. SSE는 32비트 float 4개를 한 번에 처리할 수 있으므로, 행렬곱처럼 같은 연산이 반복되는 커널에서 효과를 확인하기에 적합합니다.

위 원리의 효과를 본 프로젝트 개발 환경에서 직접 측정했습니다. 표 1은 메모리 레이아웃(AoS/SoA)의 효과를, 표 2는 SIMD의 효과를 봅니다. (표 1은 g++ `-O3 -march=native`로 배열 크기를 캐시 용량 안팎으로 키우며 순회 시간을 비교했습니다 — 하드웨어 카운터 대신 이 방식으로 지역성을 관찰. 표 2는 엔진 실제 빌드와 같은 MSVC `/O2`로 07_RenderPath에 내장된 행렬 곱 벤치를 측정했습니다.)

다만 이 결과는 행렬 곱처럼 연산 밀도가 높고 데이터 접근 패턴이 규칙적인 커널에서의 측정입니다. 대규모 배열 순회처럼 메모리 대역폭이 먼저 포화되는 작업에서는 SIMD 폭을 넓혀도 같은 비율의 성능 향상을 기대하기 어렵습니다. 따라서 SIMD는 SoA와 같은 연속 메모리 배치와 함께 적용될 때 효과가 가장 분명합니다.

종합하면, 큰 성능 이득은 두 축에서 나옵니다. 대규모 데이터에서는 레이아웃(SoA)이, 연산 집약 커널에서는 SIMD가 결정적입니다. 두 결과 모두 "병목은 연산보다 메모리 접근"이라는 본 절의 논지와 일관됩니다.

1) 사용 기술 개요

DirectX 12(D3D12)는 하드웨어에 대한 명시적 제어와 멀티스레딩 최적화에 강점을 가지는 저수준 그래픽스 API입니다. 본 구현의 목표는 dy_engine의 RHI(Render Hardware Interface) 시스템에 D3D12 백엔드를 연동하고, 화면 출력까지의 렌더링 파이프라인을 구축하는 것입니다.

2) 기술 적용 방식

• 초기화 및 장치 구성: D3D12를 통해 DXGI 팩토리를 생성하고, 최적의 GPU를 탐색하여 논리적 디바이스를 초기화했습니다. 이와 함께 부드러운 화면 출력을 담당하는 스왑체인과 렌더 타겟 뷰(RTV)용 서술자 힙을 구성했습니다.

• 파이프라인 및 리소스 관리: D3D12PipelineState 클래스를 활용해 렌더링 상태와 셰이더 리소스 바인딩 규칙(Root Signature)을 정의했습니다. D3D12Buffer 및 D3D12Texture를 통해 버퍼 생성과 업로드 힙(Upload Heap) 기반의 데이터 전송을 처리했습니다.

• 최신 렌더링 아키텍처 적용: 엔진의 최신 렌더링 구조 개편에 맞춰 D3D12Device 내부에 글로벌 디스크립터 힙(Global Descriptor Heap)을 설계했습니다. 이를 통해 셰이더 내에서 배열 형태로 다수의 텍스처에 한 번에 접근할 수 있는 Bindless Texture 기법을 구현했습니다.

• 명령 처리 흐름: D3D12CommandList 객체를 구현하여 RHI 인터페이스 기반의 드로우 콜, 뷰포트 설정, 리소스 배리어 등의 명령을 할당자에 기록하고, 이를 명령 큐에 제출(ExecuteCommandLists)하여 프레임을 렌더링했습니다.

2) 기술 적용 방식

본 구현에서는 MetalDevice 클래스를 중심으로 Metal 초기화와 프레임 처리를 구성하였다. MetalDevice에서는 MTLDevice 생성, CAMetalLayer 연결, MTLCommandQueue 생성을 수행하여 렌더링에 필요한 기본 장치 구성을 완료하였다.

렌더 파이프라인 구성은 MetalPipeline 클래스에서 수행하였다. MSL 셰이더 소스를 런타임에 텍스트로 읽어 newLibraryWithSource로 컴파일하고, MTLRenderPipelineDescriptor를 구성하여 파이프라인을 생성하였다.

리소스 생성은 MetalBuffer, MetalTexture 클래스를 통해 처리하였다. Shared 모드 버퍼로 Vertex/Index 데이터를 GPU에 업로드하고, MTLTextureDescriptor를 통해 텍스처를 생성하였다.

실제 렌더링 흐름은 BeginFrame → CommandList 기록 → Submit → Present 순서로 구성하였다. MetalCommandList는 렌더패스 설정, 파이프라인 바인딩, PushConstants 전달, DrawInstanced 호출 등의 명령을 담당한다.

헤더 오염 방지를 위해 모든 Metal Objective-C 타입은 Pimpl 패턴으로 .mm 파일 내부에만 존재하도록 격리하였으며, 헤더에는 struct Impl; 전방선언만 노출하였다.

따라서 구현 범위는 C++17 기반 RHI 인터페이스 구현, Vulkan SDK를 이용한 장치 및 스왑체인 구성, CMake와 glslangValidator를 통한 셰이더 빌드 자동화, GLFW 기반 화면 연결을 포함하되, 최종적으로는 그림자 전용 패스와 메인 렌더 패스를 하나의 렌더링 흐름으로 연결하는 데 초점을 두었다. 특히 공통 셰이더 레이아웃 정의를 분리하여 C++ 코드와 GLSL 셰이더가 같은 바인딩 번호, 텍스처 사용 플래그, 소량 상수 데이터 위치를 공유하도록 만들었고, 이 구조가 조명/그림자 셰이더의 기준점이 되도록 정리하였다.

2) 기술 적용 방식

초기 Vulkan 백엔드에서는 실행 인스턴스, 화면 연결, 물리/논리 장치, 큐 계열, 스왑체인, 화면 출력 이미지를 구성하여 기본 렌더링 기반을 마련하였다. 이후 프레임 동기화 객체와 프레임별 이미지 사용 상태를 관리하여 이미지 획득, 명령 기록, 큐 제출, 화면 출력 순서를 안정화하였다. 이 부분은 단순 프레임 출력뿐 아니라 빛과 그림자에서도 중요했는데, 조명 상수 데이터와 그림자 행렬이 프레임 사이에서 어긋나면 빛이 깜빡이거나 그림자 위치가 순간적으로 흔들려 보였기 때문이다. 프레임 진행 순서와 리소스 바인딩 갱신 흐름을 정리하면서 이 문제가 사라졌고, 조명 방향과 그림자 결과가 프레임마다 일관되게 유지되었다.

렌더링 파이프라인은 메인 렌더 패스와 그림자 패스를 분리하여 구성하였다. 메인 렌더 패스에서는 텍스처, 조명 상수 데이터, 그림자 맵, 그림자 행렬 데이터, 정점/인덱스 저장 버퍼를 GPU 리소스 바인딩 묶음에 연결하고, draw별 변환 행렬과 재질 값은 소량 상수 데이터로 전달하였다. 일반적인 정점 입력 방식에만 의존하지 않고 정점/인덱스 데이터를 저장 버퍼로 넘긴 뒤 셰이더에서 인덱스를 기준으로 읽는 셰이더 기반 지오메트리 읽기 구조를 사용하여, RHI 레벨의 지오메트리 연결을 단순화하고 셰이더 데이터 규칙을 명확히 통제할 수 있게 하였다.

빛과 그림자 처리에서는 장면에 등록된 대표 방향광 또는 점광 정보를 조명 상수 데이터로 변환하고, 그림자 맵 계산 단계에서 얻은 광원 시점 행렬을 그림자 행렬

데이터로 전달하였다. 그림자 생성 여부는 해당 draw가 그림자 패스에 참여할지 결정하고, 그림자 수신 여부는 픽셀 셰이더에서 그림자 맵 샘플링을 적용할지 결정하도록 분리하였다. 조명 계산은 Phong 모델의 확산광/반사광 개념을 참고하여 시작했지만, 상위 Vulkan 셰이더에서는 GGX, Smith 기하 감쇠, Schlick Fresnel을 사용하는 마이크로패싯 기반의 간이 PBR 직접광 모델로 확장하였다. 그림자는 shadow mapping을 기반으로 깊이값 비교, 광원 시점 좌표 변환, 깊이 보정값, PCF 샘플링을 적용하여 self-shadowing, shadow acne, 경계 aliasing을 완화하였다.

2. 기능 설계

본 절은 앞의 관련 기술 연구와 백엔드 구현 경험을 바탕으로, 엔진 구조를 어떤 기능 단위로 나누어 설계했는지 정리합니다. 설계 방향은 데이터 지향 배치, 저수준 그래픽스 API를 얇게 감싸는 RHI, 멀티코어 환경을 고려한 실행 모델, 향후 Compute Shader, Mesh Shader, Ray Tracing 확장성으로 나뉩니다. 아래 여섯 영역은 데이터 레이아웃 - RHI - 실행 모델 - 렌더링 - 확장 - 설계 원칙 순으로 이 방향에 대응합니다.

1) 데이터 지향(DOD, Data-Oriented Design) 메모리 레이아웃

렌더링 시뮬레이션의 반복 실행에서는 ‘Object’를 직접 순회하기보다, Transform (Position, Rotation), Physics (Velocity, Mass), Material (Index, Parameters)처럼 용도별 데이터를 별도의 플랫 배열로 분리합니다. 예를 들어 물리 갱신 시 CPU는 필요한 Velocity와 Mass 배열만 선형으로 읽으며, 이 구조는 캐시 라인 안에서 실제로 사용하는 데이터의 비율을 높입니다. 16바이트로 정렬된 연속 데이터는 SSE 기반 SIMD 처리에도 적합합니다.

2) RHI (Render Hardware Interface)

Vulkan, D3D12, Metal 같은 저수준 그래픽스 API를 얇고 투명하게 감싸는 계층입니다. 그래픽스뿐 아니라 향후 도입할 Compute Shader, Mesh Shader, Ray Tracing 커맨드까지 동일한 인터페이스에서 capability 단위로 노출하도록 설계합니다.

IDevice (Factory): 스왑체인 관리, 리소스 생성, 전역 동기화의 정점입니다. 모든 리소스는 이 팩토리로만 생성되며 백엔드 구현은 외부에 노출되지 않습니다.

상위 렌더러와 하위 RHI를 잇는 데이터 통로입니다. 렌더 패킷 생성과 정렬, Bindless 바인딩으로 드로우를 처리하고, 패스 간 의존성, 리소스 수명, 배리어는 Render Graph가 자동 산출합니다.

Render Graph	패스의 읽기/쓰기 리소스 선언	실행 순서와 배리어 자동화, Transient aliasing

• Flattened Render Queue: 정렬 가능한 평탄 패킷을 생성하며 Sort Key는 [Depth(24)|PSO ID(24)|Instance ID(16)]입니다. 불투명 객체는 Front-to-Back로 정렬해 Overdraw를 줄이고 동일 PSO 패킷을 묶어 상태 변경을 최소화합니다.

• Bindless 전략: 백엔드별 디스크립터/argument 리소스 테이블을 통해 리소스를 인덱스로 참조하고, 소량 데이터는 각 API에 맞는 상수 전달 경로로 주입합니다.

• Render Graph: 각 패스가 사용할 리소스를 읽기/쓰기로 선언하면 그래프가 실행 순서와 리소스 배리어/동기화 명령을 자동 산출합니다. G-buffer 등 일시적 리소스는 Transient 풀에서 aliasing 재사용하며, 3절의 멀티스레드 패스 기록과 결합됩니다.

===== 22쪽 =====

5) GPU 연산 확장 (Compute Shader, Mesh Shader, Ray Tracing) — 확장 계획

명시적 API의 최신 파이프라인을 단계적으로 도입해 CPU 의존을 줄이고 처리량을 높입니다. (현재 미구현, 로드맵 Phase 4~6.)

핵심 메커니즘	세부 기술	설계 목적
Compute Shader	DispatchCompute, GPU 컬링과 포스트프로세싱	CPU 병목 완화와 대역폭 활용
Mesh Shader	Task→Mesh 파이프라인, meshlet	GPU-driven geometry, 드로우 콜 급감
Ray Tracing (도전)	BLAS/TLAS, ray query와 Ray Tracing 파이프라인	하이브리드 그림자, 반사, AO

• Compute Shader: Compute PSO와 `DispatchCompute()`를 추가해 프러스텀 컬링, 오클루전 컬링, tiled/clustered 라이트 컬링, bloom, tone mapping을 GPU에서 수행합니다.

• Mesh Shader: 고정 IA와 VS 단계의 일부 역할을 Task→Mesh 셰이더로 옮기고 지오메트리를 meshlet 단위로 분할하면, GPU 기반 컬링과 결합해 드로우 호출과 CPU 지오메트리 처리 부담을 줄일 수 있습니다.

• Ray Tracing (도전 과제): BLAS/TLAS 가속 구조를 빌드하고 Ray Tracing 파이프라인 또는 inline ray tracing으로 그림자, 반사, AO를 하이브리드로 처리하며, DXR과 `VK_KHR_ray_tracing`에 매핑합니다.

6) 설계 원칙

• Header Isolation. RHI 모듈은 플랫폼/백엔드 헤더(`Windows.h`, `vulkan.h`)를 노출하지 않으며 구현은 Internal 클래스와 Pimpl로 은닉합니다.

• Data-Only Communication. 모듈 간 통신은 무거운 객체 대신 POD 구조체나 인덱스(ID)로 하며, 직렬화와 네트워크 전송에도 유리합니다.

Metal 객체를 C++ 코드에서 void 포인터 형태로 넘겨야 하는 경우가 있었는데, 이때 단순히 포인터를 변환하는 것과 객체의 소유권까지 넘기는 것은 다르다는 점을 확인했습니다. 소유권 이전을 잘못 처리하면 객체가 너무 빨리 해제되거나 반대로 해제되지 않아 메모리 누수가 발생할 수 있습니다. 이 문제를 해결하기 위해 단순 참조가 필요한 경우에는 소유권을 넘기지 않는 bridge 방식을 사용하고, 실제 객체의 생성과 보관은 Metal 래퍼 클래스 내부에서 담당하도록 정리했습니다. / 세 번째 문제는 GPU 리소스의 해제 시점이었습니다. CPU 객체는 필요 없어지면 바로 삭제할 수 있지만, GPU는 커맨드 버퍼에 기록된 작업을 나중에 실행할 수 있기 때문에 리소스를 너무 빨리 삭제하면 문제가 생길 수 있습니다. 예를 들어 렌더링 명령에 사용된 텍스처나 버퍼가 GPU에서 아직 사용 중인데 CPU 쪽에서 먼저 해제하면 렌더링 결과가 깨지거나 오류가 발생할 수 있습니다. 현재 구조에서는 렌더러 종료 시점에 텍스처와 파이프라인을 정리하도록 했고, 향후에는 프레임 인덱스를 기준으로 몇 프레임 뒤에 리소스를 해제하는 지연 삭제 큐를 도입하면 더 안전한 구조가 될 수 있다고 판단했습니다. / 네 번째 문제는 자동 메모리 관리가 제대로 적용되기 위해 빌드 설정도 함께 확인해야

===== 37쪽 =====

한다는 점이었습니다. Metal 파일은 Objective-C++ 파일로 컴파일되어야 하며, ARC를 사용할 경우 컴파일 옵션에서 이를 명확하게 지정하는 것이 중요합니다. 현재 구조에서는 Metal 백엔드 파일을 Objective-C++로 컴파일하는 흐름은 구성되어 있지만, ARC 사용 여부를 명확히 관리하지 않으면 Metal 객체의 자동 해제 흐름이 불안정할 수 있습니다. 따라서 이후 보완할 점으로 fobjc-arc 옵션을 명시하거나, ARC를 사용하지 않는 경우에는 생성된 Metal 객체에 대한 release 처리를 명확하게 추가해야 한다고 정리했습니다. / 마지막으로 보완해야 할 점도 있습니다. 현재 구조는 기본적인 버퍼, 텍스처, 커맨드 버퍼 관리에는 적합하지만, 실제 엔진 규모가 커지면 리소스가 많아지고 프레임마다 생성과 해제가 반복될 수 있습니다. 따라서 이후에는 Metal Heap을 이용한 리소스 묶음 관리, 프레임별 임시 리소스 관리, GPU 작업 완료 후 안전하게 해제하는 지연 삭제 구조까지 확장할 필요가 있습니다. 이번 작업을 통해 Metal의 자동 메모리 관리 방식과 C++ 엔진의 명시적 수명 관리 방식을 함께 사용하는 기본 구조를 이해하고, GPU 리소스를 안정적으로 관리하기 위한 방향을 잡을 수 있었습니다.
